# Phase 18、22、23 实验表与案例说明

## 1. 可直接放入论文的实验表

### 1.2 论文中建议的表述方式

- 若强调“方法上限/质量潜力”，优先引用 **Phase 18**：
  - 它说明在缓存安全前缀上，经过 precision patch 后，系统可以达到较高的语义正确率。
- 若强调“系统稳定性与可运行性”，优先引用 **Phase 22**：
  - 它说明 low-action 护栏和 checkpoint/resume 能把原本会 runaway 的样本稳定收住。
- 若强调“论文主线上的正式结果”，优先引用 **Phase 23**：
  - 它是目前最适合作为正文主表的 `h=50` 完整结果，因为它跑满 `100 QA`，而且没有在线 `group and summarize`、没有空回复、没有错误样本。

## 2. 正文可直接使用的结果分析

### 2.1 总体结论

从 Phase 18、22、23 可以看到一个比较清晰的趋势：随着系统从缓存前缀小样本 probe 推进到更大规模、再推进到 full-QA 正式评测，语义正确率会有所回落，但系统稳定性和 token 效率保持良好。

具体来说：

- **Phase 18** 在 `n=40` 上取得了最高的 `S_c=62.5%`，说明 precision patch 对质量确实有正向收益。
- **Phase 22** 把实验规模推进到 `n=60`，并在不引入空回复和 token runaway 的前提下完成恢复运行，说明 low-action 结构化直答护栏是有效的。
- **Phase 23** 最终把 `h=50` 推进到完整 `100 QA`，得到 `S_c=48.0%`、`S_p=24.0%`、`T=2.06K`。虽然 `S_c` 低于最优 pilot，但它是更可信的正式结果，因为它覆盖了完整测试集，而且运行过程完全可控。

因此，论文中不应把 Phase 18 和 Phase 23 当成彼此冲突的结论，而应将二者解释为：

- Phase 18 反映方法在受控前缀上的质量潜力；
- Phase 23 反映方法在完整 `h=50` 设置下的真实整体表现。

### 2.2 为什么 Phase 23 的 `S_c` 低于 Phase 18，但仍然重要

这是一个很自然的结果，而不是实验退化的异常现象。

原因主要有三点：

1. **样本覆盖范围不同**  
   Phase 18 只覆盖前 `40` 个 QA；Phase 23 覆盖完整 `100 QA`。后半段样本通常包含更多长历史、相似任务、低层动作和时间歧义，因此难度更高。

2. **pilot 与正式结果的角色不同**  
   小规模 pilot 更容易体现某些 patch 的局部收益；full-QA 更能体现系统整体鲁棒性。

3. **Phase 23 的优势在于“完整且稳定”**  
   它的 `valid=100%`，没有空回复、没有错误标记、没有隐藏在线摘要，而且 `T=2.06K` 甚至低于前面的 probe。这说明系统不是靠“多试几轮、多烧 token”换结果，而是在可控成本下完成了完整问答。

## 3. 三个阶段在论文中的推荐定位

### 3.1 Phase 18：质量最强的小规模 pilot

推荐定位：

- 放在“调参与局部修复有效性”或“pilot 结果”部分。
- 用来说明 precision patch 的确提升了语义正确率。

可直接写成：

> 在 h=50 的缓存安全前缀上，我们对 event/date 约束和目标位置约束进行修复后，`n=40` pilot 的 `S_c` 从先前版本提升到 `62.5%`，同时保持 `valid=100%`。这表明结构化约束修复能够有效减少时间和目标定位错误。

### 3.2 Phase 22：稳定性与恢复机制证据

推荐定位：

- 放在“工程稳定性”或“运行机制”部分。
- 用来说明 checkpoint/resume 与 low-action 护栏的作用。

可直接写成：

> 在 h=50 `n=60` 的实验中，系统此前曾因低层动作问题触发重复自由搜索并接近 token 上限。加入 low-action 结构化直答护栏后，实验可从 `46/60` 的 checkpoint 安全恢复并最终完成全部 `60` 个问题，且无空回复、无在线摘要、无新的 token runaway。这说明本文提出的结构化护栏不仅改善了 token 效率，也显著增强了实验可运行性。

### 3.3 Phase 23：正式 full-QA 结果

推荐定位：

- 放在正文主实验表。
- 作为目前最稳妥的 h=50 正式结果。

可直接写成：

> 在补齐全部 `50ep` history cache 后，我们运行了完整的 h=50 `100 QA` 评测。最终系统达到 `valid=100%`、`S_c=48.0%`、`S_p=24.0%`，平均 prompt token 为 `2.06K`。整个问答阶段未触发在线 summary 构建，也未出现空回复或 `###ERROR###` 样本，说明系统在完整测试集上具备较好的稳定性与成本可控性。

## 4. 案例说明草稿

### 4.1 案例 A：Phase 18 体现 precision patch 的收益

推荐写法：

> 在 Phase 18 中，系统对若干相对日期与目标匹配问题的回答明显改善。例如，针对 `put all remote control on one armchair` 这一类时间定位问题，旧版本会给出多个错误日期，而 patched 版本能够收敛到正确日期。该结果说明更严格的 target/event 约束可以减少 summary 级检索中的过召回问题。

适合强调的点：

- 不是“靠更多搜索”获得提升；
- 而是通过更严格的候选过滤减少误匹配。

### 4.2 案例 B：Phase 22 体现 low-action guardrail 的价值

推荐写法：

> 在 Phase 22 中，低层动作问题曾导致系统在自由搜索链路中反复尝试，进而逼近 prompt-token 上限。加入 low-action 结构化直答后，诸如 `put all remote control on any sofa`、`place the egg on the countertop` 等问题可以直接从 `task_lookup(...)` 的推荐答案收口，不再进入额外搜索回合。由此，系统得以从中断 checkpoint 继续运行，并最终稳定完成 `n=60` 评测。

适合强调的点：

- 这是“系统稳定性改进”的典型案例；
- 它不一定直接提升 `S_c`，但极大提升了实验可执行性。

### 4.3 案例 C：Phase 23 体现 full-QA 条件下的完整可运行性

推荐写法：

> Phase 23 的关键意义不在于取得最高的局部正确率，而在于首次在 h=50 设置下完成了完整 `100 QA`、且全程未触发隐藏在线摘要。为达到这一目标，我们先审计并补齐 `50ep` multi-history cache，再以 `--require-history-cache` 启动正式评测，从而保证问答阶段不会额外消耗不可控的 summarizer token。最终结果表明，系统在完整数据范围内可以以较低的 `T=2.06K` 保持 `valid=100%` 的稳定运行。

适合强调的点：

- full-QA 的可复现性；
- cache 审计与强制 cache 的工程价值；
- 低 token 成本下的完整运行。

## 5. 论文里建议怎么引用这三个阶段

最稳妥的写法是：

- **正文主表**：放 Phase 23。
- **正文分析段**：同时引用 Phase 18 和 Phase 22。
- **案例分析/工程实现段**：
  - Phase 18 讲质量 patch；
  - Phase 22 讲稳定性 guardrail；
  - Phase 23 讲 full-QA cache-controlled execution。

一句话总结可以写成：

> 综合来看，Phase 18、22、23 分别从“小规模质量收益”“大样本稳定恢复”“完整评测可运行性”三个侧面，构成了 Active-H-EMV 当前 h=50 实验结果的完整证据链。

## 6. 可直接复用的小结段

> 在 h=50 设置下，本文系统表现出较好的“质量-稳定性-成本”平衡。小规模 patched pilot（Phase 18）达到 `62.5%` 的 `S_c`，说明结构化 precision patch 能有效提升语义正确率；中等规模恢复实验（Phase 22）证明了 low-action guardrail 与 checkpoint/resume 机制可以消除 token runaway 并稳定完成更长前缀评测；而在完整 `100 QA` 的正式结果（Phase 23）中，系统最终实现 `valid=100%`、`S_c=48.0%`、`S_p=24.0%`、`T=2.06K`，且未触发隐藏在线摘要。以上结果表明，Active-H-EMV 虽然仍有 low-action 与 object precision 的改进空间，但已经具备可支撑论文论证的完整实验闭环。

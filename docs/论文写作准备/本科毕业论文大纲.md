## 第一章 绪论（约 4000 字）

### 1.1 研究背景

**写什么**：服务机器人长期部署中的情景记忆需求——机器人需要在连续多天多任务的交互中回答"过去发生了什么""某个物体曾在哪里""某次失败为什么发生"等回溯性问题。引出层级情景记忆（H-EMV）作为现有解决方案：它通过 L0（原始感知）→ L4+（高层摘要）的树状结构将经历组织为可检索的长期记忆。

**支撑材料**：`docs/论文写作准备/GRAF-Mem_研究内容与实验结果整理_最终版.docx` 第一章；`docs/Key Concept/正确理解h和T.md`

### 1.2 层级情景记忆的局限与研究动机

**写什么**：指出 H-EMV 的三个核心瓶颈：（1）**横向语义关联不足**——树结构天然强调父子层级，无法表达跨任务、跨时间的事件关联，纯文本相似度检索容易遗漏相关证据；（2）**记忆持续膨胀**——append-only 架构没有压缩/巩固机制，长期运行后存储和检索成本持续增长；（3）**错误持久化**——摘要一旦写入记忆便无法修改，视觉误识别或 LLM 摘要偏差会持续影响后续所有问答。

**支撑材料**：`docs/Key Concept/图检索核心思想.md`、`docs/Key Concept/遗忘模块总结.md`、`docs/Key Concept/修正模块.md`

### 1.3 研究目的与研究内容

**写什么**：在层级记忆树骨架之上构建 **GRAF-Mem**（Graph-Retrieval and Adaptive Forgetting Memory），引入三类主动维护能力：
- （1）**事件关联图与图增强检索**：从事件节点自动派生记忆图，在检索阶段支持横向图邻居扩展与联合重排，弥补纯树结构检索的不足
- （2）**基于效用的渐进式遗忘**：对新近性、独特性、重要性和图结构中心性进行综合打分，执行 Level 0/1/2 三级渐进式压缩，在保持问答稳定的前提下降低长期存储开销
- （3）**反馈驱动记忆修正**：通过错误定位、摘要覆盖与传播检测实现"从点到面"的错误修复，使长期记忆具备反馈闭环

**支撑材料**：`docs/论文写作准备/GRAF-Mem_研究内容与实验结果整理_最终版.docx` 第 1.2–1.3 节

### 1.4 本文内容安排

**写什么**：逐章概述（用"第 X 章 [...]，本章 [...]"格式，共五章）。

## 第二章 相关工作（约 5000 字）

### 2.1 机器人情景记忆

**写什么**：回顾情景记忆在机器人领域的发展脉络——从规则式日志系统到基于深度学习的视频摘要，再到最近的大模型驱动方法。重点介绍 H-EMV（层级情景记忆树）的核心设计：L0 RawDataInstant → L1 SceneGraphInstant → L2 EventBasedSummary → L3 GoalBasedSummary → L4+ HigherLevelSummary 的五层结构，以及 LLM Agent 通过交互式树展开（expand/search/collapse）检索证据的基本范式。

**支撑材料**：`README.md` 中的论文引用（https://arxiv.org/abs/2409.17702）；`em/em_tree.py` 中的数据结构定义

**写什么**：回顾基于向量搜索的记忆检索方法，以及图结构在知识检索中的应用（知识图谱、RAG 的 Graph RAG 变体等）。指出现有工作多将图用于离线可视化而非在线检索链路，GRAF-Mem 的事件图直接进入问答检索的执行路径。

**支撑材料**：`docs/Key Concept/图检索核心思想.md`、`docs/Key Concept/图检索如何提升系统性能.md`、`docs/Key Concept/GRAPH_ADVANTAGES_EXAMPLES.md`

### 2.3 记忆压缩与遗忘机制

**写什么**：回顾经典记忆遗忘模型（艾宾浩斯遗忘曲线）在计算系统中的应用，以及已有的记忆压缩/蒸馏方法。指出现有方法多为全或无删除或固定时间窗切分，缺少"渐进式软压缩"——在不同层级上施加不同程度的信息削减。

**写什么**：回顾对话系统中的反馈学习与纠错机制。指出现有方法多在训练阶段进行参数更新，而非在运行时对特定记忆条目进行非侵入式修正。GRAF-Mem 的摘要覆盖机制实现了可逆、可追溯的运行时修正。

## 第三章 GRAF-Mem：图增强检索与结构化问答（约 7000 字）

### 3.1 引言

**写什么**：本章解决 RQ1（横向语义关联不足）和 RQ2（长历史问答稳定性与 token 成本控制）。核心方法：在保留层级记忆树的同时，构建事件关联图并将其嵌入检索链路，同时引入结构化检索工具与执行护栏。

**支撑材料**：`llm_emv/memory_graph.py`；Phase 23、24 实验结果

### 3.2 事件关联图构建

#### 3.2.1 图节点与边类型设计

**写什么**：从 EventBasedSummary（L2）自动派生图节点。介绍五种边类型及其构建方法——时间相邻（TEMPORAL_ADJACENT，零成本规则）、共享物体（CO_OBJECT，零成本规则）、共位置（CO_LOCATION，零成本规则）、相似动作（SIMILAR_ACTION，低成本嵌入计算）、因果（CAUSAL，可选 LLM 推断）。控制边密度的策略（max_group_size、max_edges_per_node、候选边权重排序）。

**支撑材料**：`llm_emv/memory_graph.py` 中 `build_memory_graph`、`_build_temporal_edges`、`_build_co_object_edges` 等函数

#### 3.2.2 图构建流程与缓存

**写什么**：图从树自动派生，不需要额外标注。通过历史结构签名（`_history_structural_cache_key`）实现图缓存，相同 history 的多次评测共享同一图结构。构建在记忆巩固（遗忘）之后——遗忘先压缩树，图在精简后的节点集上构建。

**支撑材料**：`llm_emv/setup.py` 中 `create_memory_graph_cached` 函数

### 3.3 图增强检索

#### 3.3.1 语义种子召回

**写什么**：使用 all-mpnet-base-v2 嵌入模型对交互式树节点进行语义搜索。介绍 `history_search_similarity` 的计算方式（节点 index_content 与查询的最大余弦相似度）。FAISS 加速配置（flat 索引）。

**支撑材料**：`llm_emv/emv_api.py` 中 `history_search_similarity` 函数；`llm_emv/faiss_search.py`

#### 3.3.2 图邻居扩展与联合重排

**写什么**：从语义种子节点出发，沿图边扩展到邻近事件。重排公式：`score(q, n) = α·sim_vec(q, n) + β·Σ(w(e)·sim(q, neighbor)) + γ·depth_bonus(n)`。问题意图感知的边类型选择（时间类问题偏重时间边，对象类问题偏重共享物体边等）。

**支撑材料**：`llm_emv/graph_augmented_search.py`；`docs/Key Concept/图检索如何提升系统性能.md`

### 3.4 结构化检索工具与执行护栏

#### 3.4.1 工具列表与设计动机

**写什么**：将层级记忆树中的结构性信息显式暴露为可调用工具——task_list、task_lookup、object_lookup、date_lookup、event_date_lookup、temporal_neighbor、action_lookup——使 LLM Agent 不必在几十万字符历史中盲目自由搜索，而是通过结构化路径定位证据。

**支撑材料**：`llm_emv/emv_api.py` 中 `EMVerbalizationAPI` 类的各 `@group('util')` 方法；Phase 9、10、11 记录

#### 3.4.2 缓存、checkpoint 与执行护栏

**写什么**：multi-history cache 预构建避免在线摘要调用；cache audit / require-cache 确保正式运行无隐藏摘要成本；checkpoint / resume / retry 支持长运行中断恢复；单样本和平均 prompt token 上限防护异常样本；短对象护栏（如 "cd" 不匹配 "credit card"）。

**支撑材料**：`llm_emv/eval/dechant_qa_dataset.py` 中缓存逻辑；Phase 14、17、19、23 记录中关于缓存和护栏的改进

## 第四章 效用引导的渐进式遗忘（约 7000 字）

### 4.1 引言

**写什么**：本章解决 RQ3（长期运行中记忆存储持续膨胀）。遗忘模块的核心目标不是提高 QA 准确率，而是在保持问答能力基本稳定的前提下压缩长期记忆存储。

**支撑材料**：`docs/Key Concept/遗忘模块.md`；`docs/论文写作准备/遗忘模块的实验设计说明.md`

### 4.2 效用函数设计

#### 4.2.1 新近性（Recency）

**写什么**：基于艾宾浩斯遗忘曲线的指数衰减：`R(t) = e^(-λt)`，`λ = ln(2) / half_life`（默认 half_life = 3600s）。越久远的事件效用越低，近期的经历更容易被追问。

**支撑材料**：`llm_emv/memory_consolidation.py` 中 `compute_recency` 函数

#### 4.2.2 独特性（Uniqueness）

**写什么**：`Uniqueness(n) = 1 - mean(cos_sim(n, siblings))`。在兄弟节点中语义越独特的事件效用越高；高度重复的日常动作（如反复走来走去）效用低。这与开题报告中"增量聚类合并"的思路形成对比——用连续分数替代离散的"重复/不重复"二分法，避免了合并操作对树结构的侵入式修改。

**支撑材料**：`docs/Key Concept/遗忘模块如何完整重构.md` 第一部分的分析；`llm_emv/memory_consolidation.py` 中 `compute_uniqueness` 函数

#### 4.2.3 重要性（Importance）

**写什么**：综合四个信号：（a）用户对话（ASR 识别文本）→ +0.35；（b）动作状态异常（失败/中断）→ +0.20；（c）目标状态变化 → +0.10；（d）图度中心性 → 归一化映射到 [0, 0.35]。图度中心性使"结构枢纽事件"免受遗忘——这是图结构与遗忘模块"一图两用"的关键交叉点。

**支撑材料**：`llm_emv/memory_consolidation.py` 中 `compute_importance`、`_build_temp_graph_for_centrality` 函数

### 4.3 渐进式遗忘策略

#### 4.3.1 三级遗忘操作

**写什么**：详细介绍 Level 0/1/2 的操作与适用场景。

| 等级 | 条件 | 操作 | 节省空间 | 对问答的影响 |
|------|------|------|---------|------------|
| Level 0 | U ≥ θ₁ | 完整保留 | 0% | 支持全部问答类型 |
| Level 1 | θ₂ ≤ U < θ₁ | 删除 L0 原始感知数据（图像、声音），保留文本 | ~80% | 细节问答受限，摘要问答正常 |
| Level 2 | U < θ₂ | 压缩为摘要保留：清空 scenes、relations、objects，仅保留 nl_summary | ~95% | 仅支持 overview/时间线类问题 |

**支撑材料**：`llm_emv/memory_consolidation.py` 中 `apply_forgetting_level_1`、`apply_forgetting_level_2` 函数；`docs/论文写作准备/遗忘模块的实验设计说明.md`

#### 4.3.2 遗忘豁免与安全机制

**写什么**：（1）包含用户对话的节点永不遗忘；（2）目标状态为失败的节点永不遗忘；（3）每个 Goal 的首尾事件受保护（不低于 Level 1）；（4）`min_retain_ratio`（默认 0.3）安全下限，当实际保留比例低于阈值时自动下调 θ₁ 和 θ₂。

**支撑材料**：`llm_emv/memory_consolidation.py` 中 `is_immune`、边界保护逻辑

#### 4.3.3 遗忘在图构建之前执行

**写什么**：遗忘 → 图构建的先筛后连管线。遗忘后的精简树使图构建更快、边更稀疏、图增强检索在精简后的节点集上工作。两个模块共享同一个图结构但从中获取不同的信号（检索用图边做扩展，遗忘用图中心性做保护）。

**支撑材料**：`llm_emv/setup.py` 中 `setup_llm_emv` 的执行顺序

## 第五章 反馈驱动记忆修正（约 5000 字）

### 5.1 引言

**写什么**：本章解决 RQ4（记忆错误持久化与传播）。在层级树中，`nl_summary` 是 `@property`，从底层数据动态计算，无法直接修改。本章提出摘要覆盖机制（Summary Override）——不修改底层数据，而是挂载运行时属性来覆盖摘要的展示和检索行为。

**支撑材料**：`docs/Key Concept/修正模块.md`；`docs/论文写作准备/反馈修正模块论文级详解.md`

### 5.2 四阶段修正管线

#### 5.2.1 阶段一：错误定位

**写什么**：构造两个探针查询——`question + wrong_answer`（错误特征）和 `question + correct_answer`（正确特征）。对每个事件节点计算嫌疑度：`suspicion(n) = 0.6·sim(n, error_query) + 0.4·(1 - sim(n, correct_query))`。高第一项表示与错误信息相关，高第二项表示与正确信息不相关——两者兼具的节点最有可能是污染源。

**支撑材料**：`llm_emv/memory_correction.py` 中 `localize_error` 函数

#### 5.2.2 阶段二：单点修正

**写什么**：LLM 接收四个输入（原始摘要、问题、错误答案、正确答案），Prompt 指示"只修改可能错误的部分，保留所有其他信息，只输出修正后的摘要文本"。回退机制：LLM 不可用时尝试差异词替换。

**支撑材料**：`llm_emv/memory_correction.py` 中 `correct_node_with_llm`、`_simple_text_correction` 函数

#### 5.2.3 阶段三与四：传播检测与自动传播

**写什么**：从已修正节点出发，沿时间序列检查前后邻居的摘要与原始错误摘要的余弦相似度。相似度 ≥ 0.7 标记为疑似传播；≥ 0.8 自动执行类比修正。设计假设是：视觉模型在某个时刻的误识别会同时污染多个连续感知帧。

**支撑材料**：`llm_emv/memory_correction.py` 中 `detect_error_propagation`、`auto_propagate_correction` 函数

### 5.3 摘要覆盖机制与消费端集成

**写什么**：`_summary_override` 是 Python 运行时动态属性——修正内容不影响底层序列化结构，且保持可逆（`_original_summary` 保留原始版本）和可追溯（`_correction_source` 记录修正来源）。两个关键消费端适配：语义搜索（`history_search_similarity` 将覆盖文本纳入 embedding）和树节点展示（`__repr__` 优先使用覆盖摘要）。

**支撑材料**：`docs/论文写作准备/反馈修正模块论文级详解.md` 第 2.1 节

### 5.4 模拟反馈评测协议

**写什么**：同一 episode 内的所有问题共享同一份 history 对象（不进行 deepcopy）。每道题回答后，Answer Judge 进行两阶段判定（确定性快速判断 + LLM 语义判断）；只有 WRONG 触发修正。Judge 设计为保守——PARTIAL 不触发修正，体现"不确定时不乱改"的安全理念。

**支撑材料**：`docs/论文写作准备/反馈修正模块论文级详解.md` 第 3.1–3.2 节；Phase 38 记录

### 5.5 受控错误注入验证

#### 5.5.1 LLM 修正质量验证

**写什么**：向 HigherLevelSummary 节点注入 object_swap 错误（"cabinet" → "fridge"），调用 `correct_node_with_llm`。修正 100% 成功——LLM 将 "fridge" 准确修正为 "cabinet"，LLM Judge 判定 PARTIAL（语义等价）。

**支撑材料**：Phase 40 记录

#### 5.5.2 传播检测验证

**写什么**：在同一 Goal 的 22 个连续 EventBasedSummary 帧中向 5 帧注入 Toaster→Microwave 误识别。修复了 `detect_error_propagation` 中错误跳过注入节点的 bug（区分"注入未修正"与"已修正"两种覆盖状态）。传播检测召回率 **100%**（4/4 注入帧全部检测到），精确率 28.6%（10 个假阳性来自同场景未注入帧，相似度 0.71–0.95，修正操作对它们为空操作）。

#### 5.5.3 端到端闭环验证

**写什么**：将任务身份替换错误（"浇花"→"喂猫"，3 个 depth=3 节点）注入 50ep 缓存，运行完整 `--enable-correction`（n=20）。结果：0 次 WRONG 判定，0 次修正触发。Agent 的图增强检索从其他未修改的证据源找到正确的"浇花"信息，完全绕过了注入节点。这说明 GRAF-Mem 多源检索的冗余性使孤立错误极难污染最终答案。

### 5.6 讨论

**写什么**：修正机制的三个定位——（1）**部署安全网**：当感知错误是系统性的跨多帧污染时（Phase 41 已验证传播检测在此场景下 100% 有效）；（2）**交互式修正接口**：当用户直接指出错误时系统可精准定位修正（Phase 40 已验证 LLM 修正 100% 成功）；（3）**修正不触发恰是系统"不犯错"的证明**：GRAF-Mem 的多源检索鲁棒性 + Judge 的保守设计共同构成了双重安全层。

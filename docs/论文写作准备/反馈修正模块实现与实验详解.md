# GRAF-Mem 反馈修正模块：实现与实验详解

## 一、问题背景：为什么需要记忆修正？

H-EMV/GRAF-Mem 的记忆树构建依赖两个关键步骤：

1. **视觉理解**：从原始图像中提取场景图（物体、关系），可能发生误识别（如将"客厅"识别为"厨房"）
2. **LLM 摘要**：将底层事件抽象为自然语言摘要，可能产生偏差或遗漏

这些错误一旦写入记忆树，就变成了**持久化错误**。更严重的是，因为 `nl_summary` 是 `@property`（从底层 `scenes` 和 `raw` 字段动态计算），常规手段无法直接修改摘要。

修正模块的目标是：**在收到用户反馈（或标准答案）后，定位出错节点、修正摘要、并检测/修复可能受同一错误影响的相邻节点。**

---

## 二、核心设计：摘要覆盖机制

### 2.1 为什么不能直接修改 `nl_summary`

[em/em_tree.py](em/em_tree.py) 中 `EventBasedSummary.nl_summary` 的定义：

```python
@dataclass
class EventBasedSummary:  # L2
    scenes: List[SceneGraphInstant]
    audio_description: Optional[str] = None
    action_parameter_summary: Optional[str] = None

    @property
    def nl_summary(self):
        action = self.latest_raw.current_action
        graph = self.latest_scene.nl_graph_summary
        audio = '\nAudio: ' + self.audio_description if self.audio_description else ''
        # ... 从 scenes、raw 等底层字段动态拼接出摘要文本
        return f"Action: {action}{graph}{audio}..."
```

`nl_summary` 是 `@property`，无法直接赋值。它从 `scenes` 列表中的 `SceneGraphInstant` 和 `RawDataInstant` 动态计算。如果直接改底层数据（如改 `scenes[0].raw.current_action`），会破坏原始记录的一致性。

### 2.2 解决方案：属性挂载覆盖

不修改底层数据，而是在 Python 对象上**动态挂载覆盖属性**：

```python
# llm_emv/memory_correction.py

def apply_summary_override(node, corrected_summary, source=""):
    """为节点应用摘要覆盖，不修改底层数据结构"""
    # 1. 保存原始摘要（用于回溯对比）
    if not hasattr(node, '_original_summary'):
        node._original_summary = node.nl_summary

    # 2. 设置覆盖属性
    node._summary_override = corrected_summary

    # 3. 记录修正来源（用于日志追溯）
    node._correction_source = source

    # 4. 清除 embedding 缓存（强制下次语义搜索重新计算向量）
    if hasattr(node, '_embedding_cache'):
        delattr(node, '_embedding_cache')
```

**关键设计决策**：`_summary_override` 不是一个正式的数据字段，而是 Python 运行时的动态属性。它只在内存中存在，不影响 pickle 序列化的核心结构（除非显式序列化动态属性）。这确保了：

- 修正**可逆**：`_original_summary` 保留了原始版本
- 修正**可追溯**：`_correction_source` 记录了为什么被修正
- 修正**不影响底层数据完整性**：`scenes`、`raw` 等字段原封不动

### 2.3 消费端的配合修改

修正后的摘要需要被两个关键消费端感知：

#### (a) 语义搜索端：[llm_emv/emv_api.py](llm_emv/emv_api.py)

```python
def history_search_similarity(embedding_fn, query, node):
    if embedding_fn is None:
        return 0.0

    # 获取索引内容
    texts = [s for s in node.index_content if s]

    # ★ 如果节点有修正覆盖，将修正文本也加入 embedding 计算
    wrapped = getattr(node, '_wrapped', node)
    for attr in ('_summary_override', '_cached_nl_summary'):
        extra = getattr(wrapped, attr, None)
        if extra is not None:
            texts.append(extra)

    # 计算 embedding 和余弦相似度
    embedding = embedding_fn(texts)
    query_emb = embedding_fn([query])
    similarity = util.cos_sim(embedding, query_emb).max().item()
    return similarity
```

**效果**：修正后的摘要文本被纳入节点的语义向量，因此后续的语义搜索能"看到"修正内容，使修正后的节点在相关查询中正确排名。

#### (b) 展示端：[llm_emv/interactive_tree.py](llm_emv/interactive_tree.py)

`ExpandableTreeNode.__repr__` 优先使用 `_summary_override`：

```python
# 简化的逻辑
def __repr__(self):
    summary = getattr(self._wrapped, '_summary_override', None)
    if summary is None:
        summary = self._wrapped.nl_summary
    # 展示 summary ...
```

**效果**：当 Agent 展开记忆树查看节点时，看到的是修正后的摘要，而不是原始错误摘要。

## 三、四阶段修正管线

所有核心逻辑在 [llm_emv/memory_correction.py](llm_emv/memory_correction.py) 中。

### Stage 1：错误定位（Error Localization）

**目标**：找到"哪个记忆节点的内容导致了错误回答"。

**算法**：`localize_error(history, question, wrong_answer, correct_answer, embedding_fn)`

```python
def localize_error(history, question, wrong_answer, correct_answer,
                   embedding_fn, top_k=3):
    events = _collect_all_events(history)

    # 1. 构造两个"探针查询"
    error_query = f"{question} {wrong_answer}"     # 错误特征
    correct_query = f"{question} {correct_answer}"  # 正确特征

    # 2. 计算探针的 embedding
    error_emb = embedding_fn([error_query])
    correct_emb = embedding_fn([correct_query])

    # 3. 对每个事件节点计算嫌疑度
    for event in events:
        if hasattr(event, '_summary_override'):
            continue  # 已经修正过的节点跳过

        node_emb = embedding_fn(event.index_content)

        # 与错误信息的相似度
        error_sim = cosine_sim(node_emb, error_emb)
        # 与正确信息的相似度
        correct_sim = cosine_sim(node_emb, correct_emb)

        # ★ 嫌疑度公式 ★
        suspicion = error_sim * 0.6 + (1.0 - correct_sim) * 0.4
```

**直觉解释**：

- `error_sim` 高 → 节点内容与"问题+错误答案"语义相近 → 可能是污染源
- `correct_sim` 低 → 节点内容与"问题+正确答案"语义不近 → 不太可能给出正确答案

一个节点如果"包含错误信息"且"不包含正确信息"，嫌疑度就高。

**举例**：问题是"机器人在哪个房间切了苹果"，错误答案是"厨房"，正确答案是"客厅"。
- 包含"厨房+切苹果"但不含"客厅"信息的节点 → 高嫌疑度
- 包含"客厅+切苹果"的节点 → 低嫌疑度（因为它含正确信息）

### Stage 2：单点修正（Node Correction）

**目标**：对定位到的嫌疑节点生成修正后的摘要。

**首选方法：LLM 辅助修正** — `correct_node_with_llm(node, question, wrong_answer, correct_answer, correction_llm)`

```python
def correct_node_with_llm(node, question, wrong_answer, correct_answer, correction_llm):
    current_summary = get_effective_summary(node)

    system_prompt = """
    You are correcting a robot's episodic memory record based on user feedback.
    Given the original memory summary and information about what was wrong,
    generate a corrected version. Only modify the parts that are likely incorrect.
    Keep all other information intact.
    Output ONLY the corrected summary text, nothing else.
    """

    user_prompt = f"""
    Original memory summary:
    {current_summary}

    The user asked: "{question}"
    The system answered incorrectly: "{wrong_answer}"
    The correct answer should be: "{correct_answer}"

    Please generate a corrected version of the memory summary:
    """

    response = correction_llm.invoke([SystemMessage(...), HumanMessage(...)])
    return response.content.strip()
```

**关键设计**：LLM 被指示"只修改可能错误的部分，保留其他信息"。这避免了过度修正——不是重写整个摘要，而是做最小化修改。

**回退方法：简单文本替换** — `_simple_text_correction(node, wrong_answer, correct_answer)`

当 LLM 调用失败或未配置修正 LLM 时，使用规则式替换：

```python
def _simple_text_correction(node, wrong_answer, correct_answer):
    summary = get_effective_summary(node)

    # 策略 1: 直接在摘要中查找并替换完整错误答案
    pattern = re.compile(re.escape(wrong_answer), re.IGNORECASE)
    if pattern.search(summary):
        return pattern.sub(correct_answer, summary)

    # 策略 2: 提取差异词进行部分替换
    wrong_words = set(wrong_answer.lower().split())
    correct_words = set(correct_answer.lower().split())
    diff_wrong = wrong_words - correct_words
    diff_correct = correct_words - wrong_words

    if len(diff_wrong) == 1 and len(diff_correct) == 1:
        old_word = diff_wrong.pop()
        new_word = diff_correct.pop()
        # e.g. "厨房" -> "客厅"
        return re.sub(old_word, new_word, summary, flags=re.IGNORECASE)

    return None  # 无法简单替换，放弃
```

### Stage 3：错误传播检测（Error Propagation Detection）

**核心洞察**：错误往往不是孤立的。如果视觉模型在某个时刻误识别了场景，时间上相邻的多个事件节点可能都包含同样的错误。

**算法**：`detect_error_propagation(corrected_node, history, embedding_fn, max_hops=2)`

```python
def detect_error_propagation(corrected_node, history, embedding_fn, max_hops=2):
    original = corrected_node._original_summary  # 修正前的错误摘要
    corrected = corrected_node._summary_override  # 修正后的正确摘要

    # 1. 收集所有事件，找到修正节点在时间序列中的位置
    all_events = _collect_all_events(history)
    target_idx = all_events.index(corrected_node)

    # 2. 计算原始错误摘要的 embedding
    original_emb = embedding_fn([original])

    # 3. 检查时间邻居（前后各 max_hops 个）
    suspicious = []
    for hop in range(1, max_hops + 1):
        for neighbor_idx in [target_idx - hop, target_idx + hop]:
            neighbor = all_events[neighbor_idx]
            neighbor_summary = get_effective_summary(neighbor)

            # 计算邻居摘要与原始错误摘要的相似度
            neighbor_emb = embedding_fn([neighbor_summary])
            sim = cosine_sim(neighbor_emb, original_emb)

            if sim >= 0.7:  # 相似度阈值
                # 标记为疑似传播错误
                neighbor._correction_hint = {
                    'source_node_idx': target_idx,
                    'similarity_to_error': sim,
                    'original_error': original,
                    'correction_applied': corrected,
                }
                suspicious.append((neighbor, sim))
```

**直觉**：如果一个邻居节点的摘要与**修正前**的错误摘要高度相似，说明它可能也包含了同样的错误信息，应该一并修正。

### Stage 4：自动传播修正（Auto Propagation）

**目标**：对高置信度（sim ≥ 0.8）的传播错误自动应用类似的修正。

两种策略：
- **有 LLM**：告诉 LLM"节点 A 做了从 X 到 Y 的修正，请对相似的节点 B 做同样的修正"
- **无 LLM**：从源修正中提取差异词对（如"厨房"→"客厅"），在邻居摘要中做相同替换

### 主管线：`correction_pipeline()`

四次调用的串联：

```python
def correction_pipeline(history, question, wrong_answer, correct_answer,
                        embedding_fn, correction_llm=None, ...):
    # Stage 1: 错误定位
    suspects = localize_error(history, question, wrong_answer,
                              correct_answer, embedding_fn)

    # Stage 2: 单点修正
    corrected_nodes = []
    for node, suspicion in suspects:
        if suspicion >= suspicion_threshold:  # 默认 0.3
            corrected = correct_node_with_llm(node, ...)
            if corrected:
                apply_summary_override(node, corrected)
                corrected_nodes.append(node)

    # Stage 3: 错误传播检测
    for node in corrected_nodes:
        suspicious = detect_error_propagation(node, history, embedding_fn)

    # Stage 4: 自动传播修正
        if auto_propagate:
            auto_propagate_correction(node, suspicious, correction_llm)
```

## 四、评测协议：模拟反馈闭环

标准评测中，每道题拿到一份独立的 `deepcopy(history)`——即每题从完全相同的初始状态开始，互不影响。

修正评测的设计完全不同：**同一 episode 内的多道题共享同一份 history 对象**，后续问题能看到前面问题对记忆树的修改。

### 实现：[llm_emv/eval/qa_eval.py](llm_emv/eval/qa_eval.py) — `run_evaluation_with_correction`

```python
def run_evaluation_with_correction(model, dataset, correction_fn, answer_judge_fn):
    current_episode_key = None
    shared_history = None  # ★ 共享的 history 对象

    for sample in dataset:
        # 1. 检测 episode 边界（通过 sample_id 前缀）
        episode_key = sample.sample_id.rsplit('-', 1)[0]

        if episode_key != current_episode_key:
            # 新 episode 开始 → 使用这个 sample 的 history 作为共享 history
            current_episode_key = episode_key
            shared_history = sample.history  # ★ 所有同 episode 问题共享此对象
        # 否则：复用 shared_history（可能已被前一道题的修正管线修改过）

        # 2. Agent 用共享 history 回答问题
        hypothesis = model(sample.question, sample.question_time, shared_history)

        # 3. 模拟反馈：用 Answer Judge 判断答案是否正确
        is_correct, judge_reason, score = is_answer_correct(
            hypothesis,                 # Agent 的回答
            sample.answer,              # 标准答案（ground truth）
            sample.question,            # 原始问题
            answer_judge_fn,            # LLM Judge
        )

        # 4. 如果答案被判定为 WRONG，触发修正管线
        if not is_correct:
            correction_fn(shared_history, sample.question, hypothesis, sample.answer)
            # shared_history 被 in-place 修改

        # 5. 下一个问题 Q_{i+1} 将使用修正后的 shared_history
```


### Answer Judge 的判定逻辑

[llm_emv/eval/qa_eval.py](llm_emv/eval/qa_eval.py) — `is_answer_correct()`

Judge 分两阶段：

**Stage 1：确定性快速判断**（免费，无 LLM 调用）：
1. 完全匹配 → CORRECT
2. 标准答案是 hypothesis 的子串 → CORRECT
3. 标准答案的 token 序列包含在 hypothesis 中 → CORRECT
4. hypothesis 是标准答案的子串且足够长 → CORRECT

**Stage 2：LLM 语义判断**（仅在 Stage 1 无法确定时）：
- 调用 Judge LLM（如 `gemini-2.5-pro`）
- 输出 CORRECT / PARTIAL / WRONG
- **只有 WRONG 触发修正**；PARTIAL 视为"不需要修正"

Judge 的 prompt 明确要求：
> "Use WRONG only when the answer is clearly wrong. When uncertain between CORRECT and PARTIAL, choose PARTIAL."

这导致了一个关键实验发现：在 Phase 38–39 的 96 次 LLM Judge 判定中，85 次为 PARTIAL，**0 次为 WRONG**。

### 核心发现

1. **修正管线代码完全健康**：Smoke 验证了共享 history → Judge 判定 → 条件触发的全链路
2. **Answer Judge 极其保守**：96 次 LLM 判定中 0 次 WRONG（85 次 PARTIAL），修正从未被触发
3. **共享 history 协议本身导致 40% 答案差异**：即使不触发修正，同 episode 内共享记忆状态就足以大幅改变系统行为

## 八、关键设计决策与论文叙事

### 决策 1：PARTIAL ≠ 触发修正

PARTIAL 被设计为"不修正"——只有明确的 WRONG 才触发。这是因为在机器人记忆场景中，**不确定时不应该修改记忆**。误修正（把正确的记忆改错）比漏修正（没改错误记忆）的危害更大。

### 决策 2：摘要覆盖而非数据修改

`_summary_override` 是 Python 运行时动态属性，不侵入底层数据结构。这确保了修正可逆、可追溯，且不影响 pickle 序列化的核心结构。

### 决策 3：修正在图构建之前还是之后？

修正模块当前设计为**在运行时按需触发**（收到反馈后），而非在图构建前批量执行。这意味着修正发生在 Agent 交互过程中，修正后的节点 embedding 被即时更新。

### 论文中的定位

根据 Phase 38–39 的实验结果，论文中修正模块的建议写法：

- **方法章节**：完整描述四阶段管线（这是创新点五）
- **实验章节**：
  - **机制级验证**：合成错误注入实验（受控、可重现、强证据）
  - **系统级发现**：共享 history 协议导致 40% 答案差异（验证了反馈闭环的 statefulness）
  - **坦诚说明**：当前图增强检索精度下自然问答极少触发修正，修正机制更多是安全网
- **不要声称**：修正显著提升了 benchmark 准确率

# GRAF-Mem 反馈修正模块实验规划

## 当前状态

修正模块代码已全部实现（`llm_emv/memory_correction.py` 约 670 行），评测管线支持 `--enable-correction`。但仅做了机制级 smoke 验证，尚未进行系统性量化评测。

已有 4 个 YAML 配置覆盖修正实验矩阵：

| 配置 | 图增强 | 修正 | 传播检测 |
|------|--------|------|----------|
| `full_graph_aug_correction.yaml` | ✓ | ✓ | ✓ |
| `full_correction_only.yaml` | ✗ | ✓ | ✓ |
| `full_correction_no_propagation.yaml` | ✓ | ✓ | ✗ |
| `full_graph_aug.yaml` (基线) | ✓ | ✗ | ✗ |

## 核心实验假设

修正模块的核心声明是：**当同一 batch 内某个问题回答错误后，修正管线定位并修复出错的内存节点，使后续问题受益于修正后的记忆。** 这需要从三个层面验证：

1. **修正管线能否正确触发和执行？**（机制有效性）
2. **修正后，后续问题的正确率是否提升？**（跨题影响）
3. **传播检测是否有增量贡献？**（消融验证）

## 实验一：Smoke Test（|h|=5，低成本全链路验证）

**目的**：跑通 `--enable-correction` 全链路，验证修正管线无报错，收集修正统计。

**命令**：
```bash
python -m llm_emv.eval \
  --cfg teach/simplified/full_graph_aug_correction \
  --dataset teach-dechant \
  --teach-base dataset/TEACh \
  --qa-file data/teach/test_set_5.pkl \
  --output experiments/results/teach/correction_smoke_h5.json \
  --enable-correction \
  --require-history-cache
```

**关注指标**：
- 每个 batch 内修正触发了多少次
- 修正管线各阶段统计（`direct_corrections`, `propagation_detections`, `propagation_corrections`）
- Answer Judge 对每道题的判定分布（CORRECT/PARTIAL/WRONG）
- 整体流程是否报错

**预期时间**：约 10-15 分钟（100 题，|h|=5 历史很短）

## 实验二：主实验 — 修正 vs 无修正（|h|=50）

**目的**：量化修正机制对同 batch 后续问题正确率的影响。

**核心设计**：需要两组对比：

### 组 A：共享 history + 无修正（新基线）

当前 Phase 23 的结果是每题独立 deepcopy history（标准模式），不是共享 history。共享 history 本身就会改变行为（树状态跨题保持）。因此需要先跑一个新的共享 history 基线。

通过将 `correction.enabled` 设为 `false` 但走 `run_evaluation_with_correction` 路径（correction_fn=None）实现。此时同 batch 内共享 history，但触发的修正被跳过。

### 组 B：共享 history + 修正

```bash
python -m llm_emv.eval \
  --cfg teach/simplified/full_graph_aug_correction \
  --dataset teach-dechant \
  --teach-base dataset/TEACh \
  --qa-file data/teach/test_set_50.pkl \
  --output experiments/paper_formal/teach_active_h_emv_20260424/phaseXX_h50_correction_full/h50_correction_full.json \
  --enable-correction \
  --require-history-cache
```

### 分析维度

**① 按 batch 内问题位置分析**（最核心的分析）：

Batch 内问题顺序: Q1 → Q2 → ... → Q10。越后面的问题受益窗口越大。如果修正有效，组 B 在 position ≥ 2 的题目上应有更高的 S_c/S_p。

**② 按问题类型分析**：

某些问题类型（如 `sequence_of_task_descs`、`tasks_to_days_ago`）依赖更宏观的摘要信息，修正 LLM 重写摘要后对这些类型的影响可能更大。低层动作问题（`seq_specific_shortened_low_actions`）依赖原始动作数据，修正可能无法改变。

**③ 修正统计**：

- 每个 batch 平均修正次数
- 修正节点的嫌疑度分布
- LLM修正 vs 文本替换回退的比例
- 传播检测命中率

## 实验三：消融 — 传播检测的增量贡献

**目的**：验证错误传播检测是否提供了超越单点修正的额外价值。

**命令**：
```bash
python -m llm_emv.eval \
  --cfg teach/simplified/full_correction_no_propagation \
  --dataset teach-dechant \
  --teach-base dataset/TEACh \
  --qa-file data/teach/test_set_50.pkl \
  --output experiments/paper_formal/teach_active_h_emv_20260424/phaseXX_h50_correction_noprop/h50_correction_noprop.json \
  --enable-correction \
  --require-history-cache
```

**对比**：实验二组 B（完整修正）vs 实验三（仅单点修正，无传播）

**关注**：在有多个连续错误（同一视觉误识别影响连续帧）的 batch 中，传播检测是否能多修正几个节点。

**目的**：验证图结构是否帮助修正管线更准确地定位错误节点。

使用 `full_correction_only.yaml`（无图增强，有修正）。对比实验二组 B（有图+修正）。

## 论文中的表述定位

修正模块的实验应定位为："机制级验证 + 系统闭环能力展示"，不作为主实验结果的核心支撑。

- **可以写**：修正机制在模拟反馈协议下成功执行，修正后的记忆使同 batch 后续问题的 S_c/S_p 有正向变化
- **可以写**：传播检测在连续错误场景中提供了额外的修正覆盖
- **不建议写**：修正显著提升整体 benchmark 准确率（因为修正本身只在回答错误后才触发，不直接改善首次回答的正确率）

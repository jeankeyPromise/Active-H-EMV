# 第三章 图增强检索与结构化问答

## 3.1 引言

如第二章所述，层级情景记忆树通过将原始多模态经历组织为 L0–L4+ 的五层纵向结构，配合 LLM Agent 的交互式树导航，以远低于完整历史 flatten 方案的 token 成本实现了长历史问答。然而，树的检索范式是纯纵向的——Agent 沿父子关系展开节点，证据召回的上限由树的层级结构和文本语义相似度决定。许多回溯性问题天然依赖跨任务、跨时间的横向联系——例如"这个杯子后来出现在哪些任务中""那次失败之前发生了什么""同一位置还有哪些事件"——这些问题的答案分散在树的不同分支和层级中，仅靠纵向展开和文本搜索极易遗漏关键证据。

本章解决第一章所提出的第一个研究问题（RQ1）：如何在长历史条件下，弥补纯层级结构和文本相似度检索在横向语义关联上的不足。核心方法是在不修改树存储结构的前提下，在树之上插入一层**事件关联图**索引：从 L2 事件节点自动派生图节点，构建时间、物体、位置、动作和因果五类语义边，将横向联想能力嵌入检索链路。同时，将记忆树中的任务、物体、日期等结构化信息显式化为可调用工具，并配合预处理缓存和执行护栏，使 Agent 在长历史上的搜索行为从"盲目自由展开"转变为"沿结构化路径精确命中"。

本章 3.2 节介绍事件关联图的构建方法——节点派生、五类边的定义与构建算法、密度控制与缓存策略。3.3 节介绍图增强检索的三阶段流水线——语义种子召回、图邻居扩展与联合重排。3.4 节介绍结构化检索工具与执行护栏的设计。3.5 节在 TEACh 数据集上报告 |h|=50 和 |h|=100 两种设置下的长历史问答实验结果和机制归因分析。

> **插图说明 3.1**：图增强检索系统整体架构图。从上至下展示：用户问题 → 查询意图分类器（激活对应边类型）→ Stage 1 语义种子召回（FAISS 向量索引）→ Stage 2 图邻居扩展（沿激活的边类型扩展到邻居节点）→ Stage 3 联合重排 → 与结构化工具结果合并 → LLM Agent 生成答案。左下角展示事件关联图从层级记忆树的 L2 层自动派生。

## 3.2 事件关联图构建

事件关联图是 GRAF-Mem 的核心数据结构。它从层级记忆树自动派生，作为树之上的横向索引层，使检索同时具备"沿树上下搜索"和"沿图横向扩展"两条路径。更重要的是，图结构在后续章节中还被遗忘模块用于中心性评估（第四章）和修正模块用于传播检测（第五章）——这种"一图多用"的设计是 GRAF-Mem 的核心创新之一。本节详细阐述图节点与边的定义和构建算法。

### 3.2.1 图节点的定义与派生

事件关联图的节点直接对应层级记忆树中的 L2 层节点（EventBasedSummary）。选择 L2 层作为图节点来源的原因有三：（1）L2 节点是记忆树中最细粒度的自然语言层——每个 L2 节点对应一个具体的操作动作（如 "Pickup(Mug_0)"）或一行用户语音，颗粒度适合作为检索的基本单元；（2）L2 节点携带的信息维度最为丰富——包含物体集合（从 L1 场景图汇总而来）、动作标签、位置签名和时间范围，可以支撑多种不同类型的边构建；（3）L2 节点的数量适中——在 |h|=50 的评测设置下约 5000–6000 个节点，构建和缓存图的成本可控。

具体派生流程如下。设记忆树共有 N 个 L2 节点 `{E₁, E₂, ..., E_N}`，对每个节点 Eᵢ 提取以下属性：

- **物体实例 ID 集合** `O(Eᵢ)`：遍历 Eᵢ 关联的所有 L1 场景图，汇总各帧中出现的物体实例 ID（如 "Mug_0"、"CounterTop_1"）
- **主要动作** `A(Eᵢ)`：从 `Eᵢ.latest_raw.current_action` 提取，如 "Pickup(Mug_0)"、"Place(CounterTop_0)"、"Noop"
- **位置签名** `L(Eᵢ)`：由于 TEACh 数据没有显式的房间标签，位置签名通过各帧场景图中的大型固定物体（家具、电器）的类别集合来近似。具体地，取该事件最后一个场景图中属于位置指示物体集合（包括 Sink、Fridge、CounterTop、Cabinet、StoveBurner、Toaster、Sofa、Bed 等 20+ 类家具/电器）的物体类别列表，排序后拼接为位置签名字符串
- **时间范围** `T(Eᵢ) = [t_start, t_end]`：从该事件对应的时间范围提取

每个图节点 `Gᵢ` 继承其源 L2 事件 Eᵢ 的上述属性，且保留对原始树节点 Eᵢ 的引用（`Gᵢ.tree_node = Eᵢ`），以支持从图节点回树节点进行细节展开。

### 3.2.2 五种边类型的定义与构建算法

事件关联图支持五种边类型，分别编码不同类型的事件间横向语义关联。每种边类型的构建算法独立运行，最终的图为它们的并集。以下按构建成本从低到高逐一阐述。

**（1）时间相邻边（TEMPORAL_ADJACENT）**

时间相邻边连接同一 Goal（L3 目标摘要）下前后相邻的两个 L2 事件。其构建为纯规则驱动，零嵌入计算成本。构建算法为：对每个 L3 Goal 节点 G，取其所包含的 L2 事件序列 `[E₁, E₂, ..., E_k]`，对序列中每对相邻事件（Eᵢ, Eᵢ₊₁）添加一条无向的时间相邻边。边的权重为固定的 1.0（因为时间相邻是确定性的结构关系，不存在"强度"变化）。

该边类型支撑"之前/之后发生了什么"类时序推理问题。例如，用户问 "what did you do just after making coffee"，Agent 可以从"making coffee"对应的图节点出发，沿时间相邻边定位到紧后的事件并展开其摘要。

**（2）共享物体边（CO_OBJECT）**

共享物体边连接涉及相同物体实例 ID 的两个 L2 事件。构建算法为：对每一对共享至少一个物体实例 ID 的事件（Eᵢ, Eⱼ），添加一条无向边。边的权重为两个事件物体集合的 Jaccard 系数：

```
w_co_object(Eᵢ, Eⱼ) = |O(Eᵢ) ∩ O(Eⱼ)| / |O(Eᵢ) ∪ O(Eⱼ)|       (3-1)
```

为避免过于常见的物体（如 "agent hand"、"Floor" 等几乎出现在所有事件中的物体）导致图过密，对纳入 Jaccard 计算的物体集合进行过滤：排除全局频率超过阈值（默认为所在 Goal 的事件数的 80%）的物体 ID。

该边类型支撑"与某个物体相关的所有事件"类问题。例如，用户问 "where else did the blue mug appear"，Agent 可以从当前已知包含蓝色杯子的图节点出发，沿共享物体边找到该杯子出现的所有其他事件位置。

**（3）共位置边（CO_LOCATION）**

共位置边连接共享相同位置签名（即场景中出现的家具/电器集合高度重叠）的两个 L2 事件。构建算法为：对每对事件计算其位置签名字符串的 Jaccard 系数（基于位置物体类别集合而非实例 ID），若 ≥ 阈值（默认 0.5），则添加一条无向边。边的权重即为位置签名的 Jaccard 系数。

该边类型支撑"同一位置还发生了哪些事"类空间推理问题。例如，用户问 "what else happened in the kitchen"，Agent 可以从 kitchen 相关事件出发，沿共位置边找到同一空间内的其他事件。

**（4）相似动作边（SIMILAR_ACTION）**

相似动作边连接动作语义相似的 L2 事件。动作相似度通过 Sentence-BERT 嵌入模型（all-mpnet-base-v2）计算。关键优化：不是对 N² 对事件-事件计算动作相似度（在 N≈6000 时不可接受），而是先提取唯一的动作类型集合 `A* = unique({A(E₁), ..., A(E_N)})`（通常 M = |A*| ≪ N，因为大量事件共享相同或相似的动作），仅计算 M² 对动作-动作的语义相似度，再将其映射回事件对。对动作对相似度超过阈值（默认 0.85）的事件对，添加一条无向边，边权重等于动作对的余弦相似度。

该边类型支撑"类似的操作还执行过哪些"类泛化检索。例如，用户问 "when else did you clean something"，Agent 可以找到所有包含 "clean" 相关动作（如 "rinse"、"wipe"、"wash"）的事件。

**（5）因果边（CAUSAL）**

因果边尝试连接存在因果或失败传播关系的两个事件。其构建依赖 LLM 推断，成本较高，因此默认为可选启用。构建算法为：对每个 Goal 内的事件序列 `[E₁, ..., E_k]`，识别其中的异常事件（动作状态为 failure 或目标状态发生突变），将异常事件的上下文（前后各 2 个事件的摘要）发送给 LLM，由 LLM 判断任意两个事件间是否存在因果关联（如"因为上一步把杯子掉到地上打碎了，所以下一步清扫地面"）。若 LLM 判断存在因果关系，则添加一条有向因果边，权重由 LLM 给出（通常为 0.7–0.9）。

### 3.2.3 密度控制、内容签名与图缓存

五种边类型中，除时间相邻边的数量随 N 线性增长外，其余四种在全连接的情况下都会导致 O(N²) 的边数。实际构建中，通过三重密度控制确保图的规模可控：（1）**全局频率过滤**：对共享物体边，过滤掉在超过 80% 事件中都出现的物体 ID（如 "Floor"、"agent hand"）；（2）**节点度上限**：对每个节点，每种边类型最多保留 top-k（默认 20）条权重最高的边；（3）**按边类型权重排序**：在有节点度上限约束的情况下，对候选边按权重降序选择，优先保留关联强度最高的边。

评测管线中，相同 history（由 episode 列表唯一确定）的多次评测调用共享同一图结构。图的缓存通过历史结构签名实现——计算节点类型、数量、时间范围和摘要文本的确定性哈希值，作为缓存的 key。若缓存命中，则直接加载已构建的图对象，避免重复的嵌入计算和边构建。在 |h|=50 的设置下，图通常包含约 5000–6000 个节点和 30000–50000 条边，构建时间约 10–20 秒（包括动作嵌入计算），缓存命中后加载仅需约 1 秒。

图构建在记忆巩固（遗忘）之后执行。遗忘模块先压缩低效用节点，图在精简后的节点集上构建——更小的树意味着更少的图节点、更稀疏的边、更聚焦的检索。这种"先筛后连"的管线设计是第三章和第四章模块之间最重要的协作接口。

## 3.3 图增强检索流水线

图增强检索在 Agent 执行 `history.search(query)` 时被触发，将原本的纯文本相似度 top-k 返回替换为经过图扩展和联合重排后的结果列表。整个流水线包含三个阶段。

### 3.3.1 阶段一：语义种子召回

语义种子召回沿用了层级记忆树原有的语义搜索机制。使用 Sentence-BERT 的 all-mpnet-base-v2 模型（768 维嵌入）计算查询向量 q 和每个节点递归索引内容 `index_content(n)` 之间的余弦相似度。采用 max-pooling 策略——即 `sim_vec(q, n) = max(cos_sim(emb(q), emb(t)) for t in index_content(n))`——确保只要节点中有一小段文本与查询高度相关即可被召回。FAISS flat 索引用于加速大规模检索。

语义种子召回的产出是候选集 S₀，包含 top-k_sem（默认 k_sem = 10）个语义相似度最高的节点。S₀ 作为后续图扩展的起点。

### 3.3.2 阶段二：图邻居扩展

对 S₀ 中的每个种子节点 s，遍历其通过激活边类型集合 E_active 连接的邻居。E_active 不是固定的——它由**查询意图分类器**根据用户问题的关键词动态决定：若问题包含 "where" 或房间名等关键词，激活 CO_LOCATION 和 TEMPORAL_ADJACENT 边；若包含具体物体名，激活 CO_OBJECT 边；若包含 "why" 或 "cause"，激活 CAUSAL 边；默认情况下激活除 CAUSAL 外的所有边类型。

对于每种激活边类型 e，从 s 出发最多取 max_neighbors（默认 10）个权重最高的邻居，所有邻居的集合为扩展集 S₁。图邻居扩展的直观意义是：如果节点 s 与用户问题高度语义相关，那么与 s 具有时间/物体/位置/动作关联的邻居节点也可能包含对回答有用的信息——即使这些邻居的文本与问题在措辞层面并不相似。

### 3.3.3 阶段三：联合重排

将 S₀ 和 S₁ 合并为候选池 S = S₀ ∪ S₁，对 S 中的每个节点 n 计算联合重排分数：

```
score(q, n) = α · sim_vec(q, n)
            + β · Σ_{e ∈ E(n) ∩ E_active} w(e) · mean( sim_vec(q, n') for n' in neighbors(n, e) )
            + γ · depth_bonus(n)                                  (3-2)
```

其中三项语义分别为：

- **第一项（α 项）**：节点自身与查询的语义相似度。这是原有纯语义搜索的能力，确保检索结果始终以语义相关性为基底。
- **第二项（β 项）**：图邻居的加权贡献。对于节点 n 通过激活边类型连接的所有邻居 n'，计算邻居与查询的语义相似度，按边权重 w(e) 加权求和后取平均。这一项使"虽然自身语义相似度一般，但有多个高相关邻居"的节点获得提权——因为这些节点可能是连接多个相关事件的结构枢纽。
- **第三项（γ 项）**：深度奖励。`depth_bonus(n) = (max_depth - depth(n)) / max_depth`，其中 max_depth 为当前树的深度（默认 6），depth(n) 为节点所在层级（根为 0）。层级越浅（越宏观的摘要）获得越高的深度奖励——因为在记忆树中，浅层节点覆盖的时间范围和语义内容更广，对 overview 类问题更有价值。

权重默认设置为 α=0.70, β=0.25, γ=0.05。α 的主导地位（0.70）确保语义相关性始终是排序的最主要依据；β=0.25 为图结构信号提供了足够的表达空间，但不会使其压倒语义相关性；γ=0.05 给予浅层节点微弱的偏好，在不改变排序主导逻辑的前提下提供结构先验。

最终，按联合重排分数降序返回 top-k_rerank（与 S₀ 的 k_sem 相同，默认 10）个节点给 Agent，Agent 随后可以在这些节点上执行 expand/search/collapse 等进一步操作。

## 3.4 结构化检索工具与执行护栏

### 3.4.1 工具设计：将树结构暴露为可调用能力

除了图增强的语义搜索，GRAF-Mem 将层级记忆树中的结构性信息显式化为七种可调用工具。这些工具直接利用树的时间、任务和物体结构进行确定性或半确定性查找，避免了 Agent 在几十万字符历史中进行盲目自由搜索。每个工具的内部实现均不涉及额外的 LLM 调用——它们直接读取树节点中的结构化字段并格式化返回。

**（1）task_list(max_tasks=30)**：按时间顺序返回记忆树中所有任务级摘要（GoalBasedSummary 的 nl_summary）。对应"列出你做了哪些任务"类问题，直接给出按时间排列的任务清单，Agent 无需展开任何节点即可回答 task-list 类问题。

**（2）task_lookup(query, max_matches=8)**：在任务级摘要中使用嵌入向量匹配与 query 最相关的 top-k 个任务，返回每个匹配的摘要文本和对应的时间范围。对应"描述了某个任务的细节"类问题。

**（3）object_lookup(object_name, max_matches=8)**：在所有 L2 事件摘要中查找提及指定物体名称（支持子串匹配）的事件，按时间排序。内部先做字符串子串匹配，再对候选集用嵌入向量精排。对应"某物体出现在哪些任务中"类问题。关键防护：对长度 ≤ 3 的短物体名（如 "cd"），要求精确匹配而非子串匹配，防止 "cd" 漂移到 "credit card" 等噪声匹配。

**（4）date_lookup(query, max_matches=8)**：解析 query 中的日期或相对天数表达式（如"21 days ago""November 23, 2023"），在树中定位对应时间范围内的事件摘要。返回格式包含日期、事件摘要和语义匹配分数。对应"某天做了什么"类问题。

**（5）event_date_lookup(query, max_matches=12)**：针对"how many days ago did you do X"类问题的专用工具。解析 query 中的事件描述和目标日期，找到所有匹配事件并计算距目标日期的天数。返回格式为 "score=X; days_ago=Y; date=Z: summary"。

**（6）temporal_neighbor(target_task, direction, max_candidates=6)**：给定一个目标任务描述，在树中找到对应事件，然后沿时间方向（before/after）返回相邻的任务候选。内部通过 task_lookup 定位目标 → 沿时间相邻边或树结构找到前后邻居。对应"X 任务之前/之后做了什么"类问题。

**（7）action_lookup(query, max_matches=6)**：针对低层动作问题，将原始 L2 事件级动作映射回其所属的任务级摘要。对应"当你执行某个具体动作时正在完成什么任务"类问题。当低层动作已通过结构化工具给出高置信答案时，Agent 直接使用 `answer()` 返回，不再进入自由工具循环——这种"结构化直答"机制有效减少了低难度问题的 token waste。

### 3.4.2 缓存体系与执行护栏

长历史评测的稳定性不仅依赖于检索算法本身，还依赖于执行层面的系统性控制。GRAF-Mem 在评测管线上构建了三层执行护栏。

**（1）预处理缓存体系**。每个长历史（如 50 个 episode 的拼接）在正式 QA 评测之前，先通过 `--precompute-history-cache` 批量调用 LLM summarizer 生成完整的层级摘要树（递归概括直到单一根节点），将结果序列化为 pickle 文件。正式评测中，`--require-history-cache` 标志强制仅从缓存文件加载历史——不允许在 QA 过程中触发任何在线 LLM 摘要调用（如 `group_and_summarize`）。评测前的 `--audit-history-cache` 审计步骤确保所有需要的缓存文件都存在且完整。

**（2）checkpoint 与容错**。长运行（100 题 QA + 图构建 + 嵌入加载，总耗时约 30–60 分钟）支持 checkpoint / resume 机制——每个样本的答案在完成后立即写入 JSON 输出文件，中断后重新启动时自动跳过已完成的样本。对瞬时 API 错误（网络超时、限流等），单样本支持最大 2 次自动重试。

**（3）token 与时间护栏**。设置单样本 prompt token 上限（默认 12000）和平均 prompt token 上限（默认 4000），防止异常样本因反复搜索导致 token runaway 拖垮整轮实验。单样本运行时间上限（默认 180 秒）防止死循环或 API 长时间无响应导致的阻塞。

## 3.5 TEACh 长历史问答实验

### 3.5.1 实验设置

本章的实验在 TEACh 数据集上进行，使用 |h|=50 和 |h|=100 两种历史长度设置。每种设置包含 10 段长历史（每段由 50 或 100 个 episode 拼接而成），每段配有 10 种不同类型的问答对，共计 100 题。TEACh 数据集的详细背景和问题类型分布见第二章 2.7.1 节。

**基线**：原始层级情景记忆框架（H-EMV）的报告结果，使用 full multimodal ICL=1 设置——即完整的多模态历史（图像+语音+动作）被扁平化为 prompt，由 GPT-4 一次性生成答案。基线在 |h|=50 和 |h|=100 下的 S_c、S_p 和 T 数据直接引用自 H-EMV 原论文的报告。

**GRAF-Mem 配置**：使用 `full_graph_aug_zs_fast` 配置，包含事件关联图（所有五种边类型，因果边除外）和全部七种结构化工具。Agent 模型为 Gemini-2.5-Pro（通过 API 调用），嵌入模型为 all-mpnet-base-v2。所有评测历史均使用预处理缓存，正式 QA 中强制 `require-cache`，无在线摘要成本。

**评测指标**：
- **S_c（Semantic Correctness，完全正确率）**：回答在语义上完全命中标准答案的比例，由 LLM Judge（Gemini-2.5-Pro，独立于 Agent 的实例）判定为 CORRECT 的比例
- **S_p（Semantic Partial，至少部分正确率）**：回答至少抓住关键事实的比例，即 Judge 判定为 CORRECT 或 PARTIAL 的比例
- **Wrong / no-answer 率**：Judge 判定为 WRONG 或系统无有效输出的比例
- **T（Average prompt tokens per QA）**：每个 QA 的平均 prompt token 消耗量，衡量检索和问答的上下文成本

### 3.5.2 主实验结果

#### 表 3-1 TEACh 长历史问答主结果

| 实验设置 | \|h\| | S_c | S_p | Wrong / no-answer | T (prompt/QA) |
|---------|------|-----|-----|-------------------|---------------|
| H-EMV baseline (ICL=1) | 50 | 37.0% | 68.0% | 32.0% | 10.2K |
| **GRAF-Mem** | **50** | **48.0%** | **72.0%** | **28.0%** | **2.06K** |
| H-EMV baseline (ICL=1) | 100 | 34.0% | 62.0% | 38.0% | 10.4K |
| **GRAF-Mem** | **100** | **49.0%** | **75.0%** | **25.0%** | **2.29K** |

> **表注**：H-EMV baseline 数据来自原论文 Table I（TEACh full multimodal, ICL=1 设置）。GRAF-Mem 数据来自 Phase 23（|h|=50）和 Phase 24（|h|=100）的完整 100/100 评测。

#### 表 3-2 GRAF-Mem 相对 baseline 的优势量化

| 对比项 | ΔS_c | ΔS_p | Δ Wrong/no-answer | ΔT |
|--------|------|------|-------------------|-----|
| \|h\|=50 GRAF-Mem vs Baseline | +11.0 pp | +4.0 pp | -4.0 pp | **−79.8%** |
| \|h\|=100 GRAF-Mem vs Baseline | +15.0 pp | +13.0 pp | -13.0 pp | **−78.0%** |

从表 3-1 和表 3-2 可以得出三个关键观察：

**（1）语义正确率显著提升。** 在 |h|=50 设置下，S_c 从 37.0% 提升至 48.0%（+11.0 个百分点）；在更长的 |h|=100 设置下，提升更为显著——S_c 从 34.0% 提升至 49.0%（+15.0 个百分点），S_p 从 62.0% 提升至 75.0%（+13.0 个百分点），同时 Wrong/no-answer 率从 38.0% 降至 25.0%（−13.0 个百分点）。GRAF-Mem 不仅在整体上优于基线，而且随着历史长度的增加，优势反而扩大——基线在 |h| 从 50 增至 100 时 S_c 下降了 3 个百分点（37%→34%），而 GRAF-Mem 基本持平（48%→49%）。

**（2）Token 成本大幅降低。** 在两个设置下，GRAF-Mem 的平均 prompt token 消耗均约为 2.1K–2.3K，仅为 baseline 的 20% 左右——降低约 78%–80%。H-EMV 的 10.2K–10.4K prompt tokens 中包含大量扁平化原始帧的展开和在线搜索的上下文，而 GRAF-Mem 的预处理缓存体系将这部分成本完全剥离。更值得注意的是，token 成本的降低并不以牺牲准确率为代价——恰恰相反，在更低的 token 预算下取得了更高的语义正确率。

**（3）|h| 敏感度低。** 当历史长度从 50 episode 翻倍到 100 episode 时，GRAF-Mem 的 S_c 仅从 48.0% 变为 49.0%（+1.0 pp），T 仅从 2.06K 增至 2.29K（+11.2%）。而基线在相同翻倍下 S_c 下降了 3.0 pp，T 反而微增（10.2K→10.4K，+2.0%）。这说明图增强检索和结构化工具在一定程度上**抵消了历史增长带来的检索难度**——事件图的横向扩展和工具的精确命中使得 Agent 不需要在更大的树中盲目搜索更多节点。

> **插图说明 3.4**：S_c 和 T 随 |h| 变化的双轴折线图。左轴（柱状图）：S_c（%），|\h|=50 和 |\h|=100 两组的 GRAF-Mem 和 baseline 并列。右轴（折线）：T（prompt tokens），两组相同。突出展示 GRAF-Mem 在 |h|=100 时 S_c 最高（49%）而 T 仅为 baseline 的 1/5。

### 3.5.3 结果分析与机制归因

GRAF-Mem 相对 baseline 的双重优势——语义正确率更高、token 成本更低——不宜归因于单一因素，而是以下三个层面的协同效应。

**（1）事件图扩展了检索覆盖面。** H-EMV 的纯文本语义搜索在面对需要横向关联的问题时容易遗漏相关证据——例如用户问"这个杯子后来出现在哪些任务中"，语义搜索可能返回包含"cup"或"mug"的事件，但可能遗漏那些虽涉及同一杯子实例但摘要文本中没有使用"cup"一词的事件（例如摘要只写了"I placed the dirty object in the sink"，而 "dirty object" 指向的就是那个杯子）。事件图的共享物体边通过 Jaccard 加权连接共享同一物体实例 ID 的所有事件，不依赖文本措辞——只要视觉场景图构建时正确地分配了同一实例 ID，就能建立连接。同样，时间相邻边确保了时序推理问题的候选事件不被遗漏，共位置边为空间推理提供了一致的关联路径。

**（2）结构化工具降低了搜索噪声。** baseline 中 Agent 需要在扁平化的长 prompt 中寻找答案，或通过通用的 expand/search 在树中自由探索。当问题涉及特定日期或特定物体时，Agent 可能反复展开不相关的分支、进行多余的语义搜索，导致 token 消耗虚高且可能被噪声信息干扰。GRAF-Mem 的结构化工具（特别是 date_lookup、event_date_lookup、object_lookup）将这种盲目搜索替换为精确的结构化查找——Agent 调用一次工具即可获得按相关性排序、包含时间/日期/分数的结构化返回，无需在 tree 中逐层展开和折叠。Phase 9–11 的记录中，task_lookup 和 date_lookup 的引入显著减少了 Agent 的自由搜索轮次。

**（3）缓存和护栏剥离了隐藏成本。** baseline 的 10.2K–10.4K prompt tokens 不仅包含 Agent 主动搜索引入的上下文，还包含评测管线在每次 `deepcopy(history)` 时可能隐含重置的树展开状态以及在线 group_and_summarize 调用（当 Agent 展开的历史范围跨越了尚未生成摘要的 episode 边界时）。GRAF-Mem 的预处理缓存 + require-cache 机制在正式 QA 开始前就确保了所有 episode 的完整层级摘要已生成并固化为 pickle 文件，评测中无任何隐藏的 LLM 摘要调用。此外，低层动作结构化直答（action_lookup 返回高置信结果时直接 `answer()` 而不进入自由工具循环）和短对象护栏阻止了常见的 token waste 模式。

综合来看，GRAF-Mem 的优势可以被概括为：**不是在让 Agent 看更多的上下文，而是在让 Agent 看到更干净、更相关的上下文**。事件图提供横向联想能力以提升召回率，结构化工具提供精确命中能力以提升精确率，缓存和护栏确保这两者在不产生隐藏成本的前提下运作。

## 3.6 本章小结

本章针对层级记忆树纵向检索在横向语义关联上的不足（RQ1），提出了事件关联图构建和图增强检索流水线。事件关联图从 L2 事件节点自动派生，包含五种语义边（时间相邻、共享物体、共位置、相似动作、因果），每种边均有明确的构建算法和密度控制策略。图增强检索通过"语义种子召回→图邻居扩展→联合重排"三阶段流水线将横向关联信号嵌入检索链路，重排公式中 α·语义项 + β·图贡献项 + γ·深度奖励项的三项加权设计确保了语义相关性始终主导排序。结构化检索工具将记忆树中的任务、物体、日期等结构信息暴露为七种可调用工具，配合预处理缓存和执行护栏，将 Agent 在长历史上的搜索行为从自由探索转变为结构化命中。

在 TEACh 数据集上的实验结果表明，GRAF-Mem 在 |h|=100 设置下达到 S_c=49.0%、S_p=75.0%、T=2.29K，相比基线 S_c 提升 15 个百分点、token 成本降低 78%。更值得注意的是，在 |h| 从 50 翻倍到 100 时 GRAF-Mem 的 S_c 基本持平，说明图增强检索在一定程度上抵消了历史增长带来的检索难度。机制分析表明，这一双重优势来自事件图的横向扩展、结构化工具的精确命中以及缓存护栏的成本剥离三者的协同。

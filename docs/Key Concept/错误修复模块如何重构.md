## 一、对初版方案的逐层剖析

### 第一层（即时修正）—— 方向正确，但有关键技术障碍

**问题 1：`nl_summary` 是只读的 `@property`，不是可写字段**

你提到"调用 LLM 重新生成该节点的摘要"，但看实际代码：

```96:129:em/em_tree.py
class EventBasedSummary:  # L2
    scenes: List[SceneGraphInstant]
    # ...
    @property
    def nl_summary(self):
        action = self.latest_raw.current_action
        action_state = self.latest_raw.current_action_state
        graph = self.latest_scene.nl_graph_summary
        # ... 从底层字段动态计算
```

`EventBasedSummary.nl_summary` 和 `GoalBasedSummary.nl_summary` 都是 **`@property`**，从底层的 `RawDataInstant` 和 `SceneGraphInstant` 字段动态计算而来。你不能简单地 `event.nl_summary = "corrected text"` —— 这会报 `AttributeError`。

所以修正不能只改摘要文本，需要设计一个**摘要覆盖机制**。

**问题 2：TEACh 评测中不存在"用户反馈"**

当前评测流程是：加载 history → 回答问题 → 对比 ground truth → 结束。没有用户反馈环节。要评测修正功能，需要设计**模拟反馈协议**。

### 第二层（模式学习）—— 与现有机制高度重叠

系统**已经有**完善的 few-shot 检索机制：

```89:91:llm_emv/simplified_agent/simple_coding_emv.py
self._retriever = SimpleFewShotRetriever(prompt_db=prompt_cfg.pop('prompt_db', []),
                                         **prompt_cfg.get('retrieval', {}))
```

`SimpleFewShotRetriever` 用 `SemanticSimilarityExampleSelector`（基于 Chroma 向量数据库）按语义相似度检索 few-shot 示例，已经实现了你说的"检索语义最相近的历史示例作为上下文参考"。

再实现一个动态 few-shot 收集器，本质上是重复造轮子，且在 TEACh 评测中存在**数据泄露**风险（用 ground truth 构造 few-shot 示例 → 再用来回答同一数据集的其他问题）。

### 第三层（关联修正）—— 最有创新价值，但描述过于笼统

这一层的核心洞察是对的：错误不是孤立的，可以沿图边传播。这与你的图增强模块形成天然的呼应。但"生成疑似关联错误列表供用户确认"在自动化评测中无法实施。

### 关于"反馈置信度过滤"和"100 轮交互提升 15%-20%"

- **置信度过滤**：好想法，但 TEACh 上无法验证（没有多轮交互）
- **100 轮 / 15%-20%**：数字太具体，没有预实验支撑不建议写。审稿人/答辩老师会追问"这个数字哪来的"

| 问题 | 影响 |
|------|------|
| `nl_summary` 是 `@property`，不可直接赋值 | 第一层无法实现 |
| TEACh 评测每题 `deepcopy(history)`，无跨题状态 | 修正效果无法跨题传递 |
| Few-shot 机制已存在 | 第二层重复造轮子 |
| 自动化评测无"用户确认"环节 | 第三层无法评测 |
| 无预实验数据 | 量化预期无依据 |

## 三、修改建议：重新设计这个模块

### 新模块名称

**基于反馈的记忆修正与错误传播抑制（Feedback-Driven Memory Correction with Error Propagation Suppression）**

砍掉"模式学习"层，聚焦两个核心能力：**单点修正** + **图引导的错误传播检测**。

### 新的总体架构

```
┌───────────────────────────────────────────────────────────────────────┐
│                    反馈驱动的记忆修正管线                                │
│                                                                       │
│  Agent 回答问题 Q₁ → 得到答案 A₁                                      │
│       │                                                               │
│       ├── A₁ 正确？→ 是 → 继续下一题                                   │
│       │                                                               │
│       └── A₁ 错误？→ 触发修正管线                                      │
│            │                                                          │
│            ├── 1. 错误定位 (Error Localization)                        │
│            │      用 Q₁ + A₁(错) + A*(对) 定位出错的记忆节点             │
│            │                                                          │
│            ├── 2. 单点修正 (Node Correction)                           │
│            │      LLM 结合反馈重写节点摘要（通过 override 机制）          │
│            │      原摘要保留为历史版本                                   │
│            │                                                          │
│            ├── 3. 错误传播检测 (Error Propagation Detection)            │
│            │      通过记忆图的 TEMPORAL_ADJACENT / CO_LOCATION 边        │
│            │      查找可能受同一错误影响的邻居节点                        │
│            │      对疑似节点标记 correction_hint                        │
│            │                                                          │
│            └── 4. Embedding 缓存失效 (Cache Invalidation)              │
│                   修正后的节点清除 _embedding_cache                      │
│                   下次搜索时重新计算，确保检索结果反映修正                 │
│                                                                       │
│  修正后的 history 传递给 Q₂, Q₃, ... （同一 episode 内共享状态）         │
└───────────────────────────────────────────────────────────────────────┘
```

### 设计详解

#### 3.1 技术基础：摘要覆盖机制（Summary Override）

由于 `nl_summary` 是 `@property`，直接赋值会失败。解决方案是引入一个 **override 字段**：

```python
def apply_correction(event: EventBasedSummary, corrected_summary: str):
    """
    为节点添加摘要覆盖。不修改底层数据，而是在节点上挂载覆盖摘要。
    
    原摘要通过 @property 仍可计算得到（保留历史版本），
    但所有需要展示摘要的地方优先使用 _summary_override。
    """
    # 保存原始摘要（用于回溯对比）
    event._original_summary = event.nl_summary
    
    # 设置覆盖摘要
    event._summary_override = corrected_summary
    
    # 清除 embedding 缓存（强制下次搜索重新计算）
    if hasattr(event, '_embedding_cache'):
        delattr(event, '_embedding_cache')
    
    # 标记修正时间和来源
    event._correction_metadata = {
        'original': event._original_summary,
        'corrected': corrected_summary,
        'timestamp': datetime.now(),
    }
```

然后在 `interactive_tree.py` 或 `emv_api.py` 中，让 `repr` 和搜索逻辑优先使用 `_summary_override`：

```python
# 在 history_search_similarity 或 index_content 计算中
def get_effective_summary(node):
    if hasattr(node, '_summary_override'):
        return node._summary_override
    return node.nl_summary
```

#### 3.2 错误定位（Error Localization）

当系统回答错误时，需要找到"哪个记忆节点的内容导致了错误"：

```python
def localize_error(
    history: HigherLevelSummary,
    question: str,
    wrong_answer: str,
    correct_answer: str,
    embedding_fn: Callable,
) -> List[Tuple[EventBasedSummary, float]]:
    """
    定位最可能导致错误回答的记忆节点。
    
    策略：
    1. 构造错误特征查询 = question + wrong_answer 的语义
    2. 在树中搜索与"错误特征"最相关的节点
    3. 排除与 correct_answer 高度一致的节点（这些节点没问题）
    
    Returns:
        按嫌疑度降序排列的 (节点, 嫌疑度) 列表
    """
```

**核心思路**：如果 agent 回答"在厨房"（错）而正确答案是"在客厅"，那么系统搜索包含"厨房"相关信息的记忆节点 —— 这些就是最可能出错的节点。

#### 3.3 单点修正（Node Correction）

定位到出错节点后，用 LLM 结合反馈生成修正摘要：

```python
def correct_node(
    node: EventBasedSummary,
    question: str,
    wrong_answer: str,
    correct_answer: str,
    correction_llm: BaseChatModel,
) -> str:
    """
    用 LLM 结合用户反馈修正节点摘要。
    
    Prompt 设计：
    "以下记忆节点的摘要可能存在错误。
     原始摘要: {node.nl_summary}
     用户指出: 对于问题 '{question}'，正确答案应该是 '{correct_answer}'
              而不是 '{wrong_answer}'。
     请根据反馈修正摘要，只修改有错误的部分，保留其他信息。"
    """
```

#### 3.4 错误传播检测（Error Propagation Detection）

**这是本模块最大的创新点**，直接复用记忆图的边关系：

```python
def detect_error_propagation(
    corrected_node: EventBasedSummary,
    correction_info: dict,  # {"错误特征": "厨房→客厅", ...}
    graph: MemoryGraph,
    embedding_fn: Callable,
    max_hops: int = 2,
) -> List[Tuple[EventBasedSummary, float, str]]:
    """
    检测错误传播范围。
    
    逻辑：如果一个节点的"客厅"被误识别为"厨房"，
    那么时间相邻的节点很可能也有同样的误识别。
    
    策略：
    1. 从修正节点出发，沿 TEMPORAL_ADJACENT 和 CO_LOCATION 边扩展
    2. 检查邻居节点的摘要是否包含相同的错误特征
    3. 按距离和特征匹配度排序
    
    Returns:
        [(疑似节点, 嫌疑度, 传播路径说明)]
    """
```

**为什么用图边而不是全局搜索**：
- 错误传播是**局部的** —— 视觉误识别通常只影响时间上相邻的帧
- `TEMPORAL_ADJACENT` 边精确定位了同一目标下的前后事件
- `CO_LOCATION` 边找到了在"同一位置"（相同错误上下文）的事件
- 这比全局搜索"包含厨房的所有节点"要精准得多

#### 3.5 评测协议：模拟反馈评测（Simulated Feedback Evaluation）

**这是最关键的设计** —— 让修正功能在 TEACh 上可评测：

```
对每个 episode:
  questions = [Q₁, Q₂, Q₃, ...]（按时间排序）
  history = load_history(episode)  # 共享一份 history，不再 deepcopy
  
  for i, (Qᵢ, A*ᵢ) in enumerate(questions):
      Aᵢ = agent.answer(Qᵢ, history)
      
      if Aᵢ 与 A*ᵢ 不匹配:
          # 模拟用户反馈：用 ground truth 作为"正确答案"
          correction_pipeline(
              history, Qᵢ, wrong_answer=Aᵢ, correct_answer=A*ᵢ,
              graph=memory_graph
          )
      
      # 修正后的 history 传递给后续问题
      # Q₂, Q₃, ... 可以受益于 Q₁ 的修正
```

**评测指标**：
- **修正前后对比**：同一 episode 的后续问题，修正组 vs 无修正组的正确率差异
- **错误传播抑制率**：修正 Q₁ 后，Q₂~Qₙ 中"因同一错误导致的错误"减少了多少
- **修正精度**：被修正的节点中，有多少确实是错的（precision）

## 六、学术叙事

论文中建议这样组织三个模块的关系：

> 本研究提出面向具身智能体的**认知启发式记忆增强框架**，包含三个协同模块：
>
> 1. **图增强检索**解决"如何更好地找到相关记忆"（检索增强）
> 2. **效用引导遗忘**解决"如何维持长期运行效率"（记忆巩固）
> 3. **反馈驱动修正**解决"如何修复错误记忆"（记忆修正）
>
> 三个模块共享同一个**记忆关联图**作为核心数据结构：
> - 图增强检索：图用于**扩展检索候选**
> - 效用引导遗忘：图的度中心性用于**指导保留决策**
> - 反馈驱动修正：图的边关系用于**追踪错误传播**
>
> 这种"一图三用"的设计体现了统一的系统性思维，而非三个独立功能的简单堆砌。
